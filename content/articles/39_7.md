## 結論

サイト本体と記事ページができたら、**GitHubへファイルを登録し、GitHub Pagesの公開元を設定**します。

この回の完成物は、第三者もブラウザから開ける公開URLです。ファイルをGitHubへ置いただけでは公開完了ではないため、Pagesの設定と公開後の動作確認まで行います。

## 1. GitHubのリポジトリを作る

GitHubへログインし、ホーム画面の左側にある「Top repositories」の緑色の「New」を押して新しいリポジトリを作ります。ワカルカモの例ではリポジトリ名は`wakarukamo`、公開URLは`https://kamowakaru.github.io/wakarukamo/`です。リポジトリ名を変えた場合、公開URLの末尾も変わります。

![GitHubホームのTop repositoriesの右にあるNewボタン](../assets/images/articles/github-dashboard-new-repository.png)

公開サイトとして使う場合は、公開範囲や登録するファイルに個人情報・秘密鍵・APIキーが含まれていないか確認します。

## 2. GitHub Desktopへリポジトリを取り込む

ブラウザから大量のファイルをアップロードすると制限に当たりやすいため、ファイル数が多い場合はGitHub Desktopを使います。

1. GitHub Desktopでリポジトリをクローンする
2. 作成したサイト一式をローカルのリポジトリへ入れる
3. 変更一覧で追加対象を確認する
4. 内容が分かるメッセージでCommitする
5. PushしてGitHubへ送る

`index.html`が想定した階層にあるか確認します。

![GitHub Desktopの変更一覧と左下のCommitボタン](../assets/images/articles/github-desktop-changes-commit.png)

上の例では変更数が多いため差分本文は表示されていません。左側のファイル一覧と、左下に書くコミットメッセージを確認してからCommitします。続けてPushします。

![Push後にGitHub上で確認できるワカルカモのフォルダー一覧](../assets/images/articles/github-repository-after-push.png)

GitHubのリポジトリ画面に`articles/`、`content/articles/`、`data/`、`scripts/`が見えれば、サイトの元ファイルと公開用ファイルを確認できます。

## 3. GitHub Pagesを設定する

リポジトリの設定からPagesを開き、公開元を選びます。

ワカルカモの設定は「Source：Deploy from a branch」「Branch：main」「Folder：/(root)」です。サイトのルートにある`index.html`と生成済みの`articles/`が配信されます。

![ワカルカモのGitHub Pages設定。Deploy from a branch、main、rootが選択され、公開URLが表示されている](../assets/images/articles/github-pages-settings-main-root.png)

画面上部の「Your site is live at」の後に公開URLが出れば、Pagesの配信先を確認できます。`.github/workflows/build-articles.yml`の「Build articles」はMarkdownからHTMLを作る処理です。**Pagesの配信設定はブランチからの公開、記事のHTML生成はActions**という別々の役割です。

自分のブログで単純なHTMLを置く場合は、GitHubの「Settings」→「Pages」で公開元を選びます。公開方式を変える場合は、生成された`index.html`が配信元に含まれるかを先に確認します。

## 4. 公開処理の完了を確認する

設定後すぐに表示されない場合があります。リポジトリ上部の「Actions」を開き、記事変更に対する「Build articles」と、その後の「pages build and deployment」が緑色のチェックで終わったか確認します。

![GitHub Actionsの実行一覧。Build articlesとpages build and deploymentの成功が緑色で示されている](../assets/images/articles/github-actions-build-and-pages-success.png)

画面には過去の実行履歴も並びます。途中に失敗した履歴があっても、今回反映したい変更の実行と、最新の配信処理を開いて結果を確認してください。

エラーが出た場合は、エラーになった工程と赤字のメッセージをChatGPTへ渡し、原因候補を絞ります。画面全体ではなく、エラーメッセージを文字で渡すと確認しやすくなります。

## 5. 公開URLを実際に開く

公開URLで次を確認します。

- トップページが表示される
- 記事一覧を開ける
- 記事本文が表示される
- CSSと画像が読み込まれる
- 内部リンクが404にならない
- スマートフォンでも表示できる

PC内で表示できても、公開先ではファイル名の大文字・小文字や相対パスの違いでリンク切れすることがあります。

## 6. 更新の流れを1回試す

記事の一文を修正し、Commit・Push・公開反映まで試します。

```text
content/articles/の記事を修正
→ Commit・Push
→ Actionsの「Build articles」の実行結果を確認
→ 生成されたarticles/内のHTMLを確認
→ 公開URLで変更箇所を確認
```

この構成ではPush後にActionsが生成HTMLをコミットします。手元で先に`python scripts/generate_site.py`を実行した場合も、どのHTMLが最終的に公開されたか公開URLで確認します。

この流れが再現できれば、今後の記事追加にも使えます。

## 今回の完成チェック

- リポジトリに秘密情報が含まれていない
- GitHub上にサイト一式がある
- Pagesの公開元を設定した
- 公開URLでトップと記事を開けた
- CSS・画像・内部リンクを確認した
- 修正から再公開まで1回試した
