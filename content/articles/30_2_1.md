## 結論

Markdownの記事をGitHub ActionsでHTMLへ自動変換するには、**MarkdownをHTMLへ変換するプログラムを用意し、GitHub Actionsからそのプログラムを実行する**構成にします。

先に決めたいのは、生成したHTMLをGitリポジトリへcommitするのか、ビルド時だけ生成して公開先へデプロイするのかです。

## ディレクトリ構成を決める

たとえばMarkdownを`content/articles`、生成HTMLを`dist`へ置く構成にします。

```text
content/
  articles/
    1.md
    2.md
scripts/
  build.py
dist/
.github/
  workflows/
    build.yml
```

実際の構成はサイトに合わせます。

## 変換処理を用意する

GitHub Actions自体が記事内容を自動でHTMLへ変換するわけではありません。

Python、Node.js、静的サイトジェネレーターなどを使い、MarkdownをHTMLへ変換する処理を用意します。

変換処理では、front matter、テンプレート、内部リンク、HTMLエスケープなど、サイトに必要な仕様も決めます。

## Workflowを作る

Workflowファイルは通常、次の場所へ置きます。

```text
.github/workflows/build.yml
```

概念的には、リポジトリを取得し、必要な実行環境を準備し、変換スクリプトを動かす流れです。

```yaml
name: Build articles

on:
  workflow_dispatch:
  push:
    paths:
      - "content/articles/**"

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build HTML
        run: python scripts/build.py
```

この例は構成を示す最小例です。`build.py`が外部ライブラリを必要とするなら、そのインストールStepも必要です。

## pathsで対象を絞る

記事Markdownが変更されたときだけ実行したい場合、`push`の`paths`で対象ディレクトリを指定できます。

これにより、記事と関係のない変更で毎回変換処理が走るのを避けられます。

## 生成HTMLをどう扱うか

方法は大きく分けて2つあります。

1. 生成HTMLをリポジトリへcommitする
2. Workflow内で生成し、その成果物をそのままデプロイする

生成物までGit管理したいか、ソースだけを管理したいかで選びます。

## 自動Commitでは無限実行に注意する

Workflowが生成HTMLをcommitしてPushし、そのPushが同じWorkflowを再び起動する設計では、意図しない再実行が起こらないよう条件を設計します。

入力Markdownだけを`paths`の対象にするなど、何がWorkflowを起動するか明確にします。

## 変換失敗時は公開しない

Markdownの構文エラーや変換スクリプトの失敗があった場合、壊れたHTMLを公開しないようにします。

変換成功後にだけデプロイStepへ進む構成にすると、失敗を検知しやすくなります。

## ローカルでも同じ変換を試せるようにする

GitHub Actions上でしか動かせない変換処理にすると、修正のたびにPushが必要になります。

同じ`build.py`などをPCでも実行できる構成にすると、ローカルで確認してからGitHub Actionsへ任せられます。

## まとめ

MarkdownからHTMLへの自動変換は、変換スクリプトとGitHub Actionsを分けて考えます。Markdown変更をきっかけにビルドし、成功したHTMLだけをcommitまたはデプロイする構成にしてください。
