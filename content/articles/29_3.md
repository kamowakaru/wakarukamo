## 結論

commitとは、**ファイルの変更内容をGitの履歴として記録する操作**です。

ファイルを編集しただけでは「履歴として1つの区切りを作った」ことにはなりません。どの変更を記録するか選び、コミットメッセージを付けてcommitします。

## commitすると何が残る？

commitには、その時点で記録対象にした変更内容と、コミットメッセージなどが保存されます。

後から履歴を見ると、どのcommitで何を変更したか確認できます。

## 保存とcommitは違う

エディタでファイルを保存する操作と、Gitでcommitする操作は別です。

保存は現在のファイル内容をディスクへ保存します。

commitは、選んだ変更をGitの履歴として記録します。

## コミットメッセージとは

commitするときは、変更内容が分かる短いメッセージを付けます。

たとえば次のようにします。

```text
トップページの見出しを修正
```

```text
記事一覧へのリンクを追加
```

`update`だけのような曖昧なメッセージより、後から見て変更内容を判断できる方が便利です。

## どのくらいの単位でcommitする？

1つの目的として説明できる変更を目安にします。

たとえば「ヘッダー修正」と「問い合わせフォーム追加」が別の作業なら、分けてcommitすると履歴を確認しやすくなります。

大量の無関係な変更を1つのcommitへまとめると、後から差分を追いにくくなります。

## GitHub上でファイルを編集した場合

GitHubのWeb画面からファイルを編集・追加するときも、変更をcommitする操作があります。

変更内容を確認し、適切なコミットメッセージを付けて記録します。

## PCでGitを使う場合の基本

コマンド操作では、一般に変更したファイルを確認し、記録対象へ追加してからcommitします。

```bash
git status
git add index.html
git commit -m "トップページの見出しを修正"
```

`git status`で状態を確認し、`git add`で記録対象を選び、`git commit`で履歴へ記録します。

## commitしただけでGitHubへ反映される？

PC上でcommitしただけでは、GitHub上のリポジトリへ変更が送られていない場合があります。

ローカルリポジトリのcommitをGitHubへ反映するには、通常pushを行います。

このため「commitできた」と「GitHubへ反映された」は分けて確認します。

## 間違ったファイルを含めない

commit前に`git status`や差分を確認し、秘密情報や不要なファイルが含まれていないか見ます。

APIキーなどを誤ってcommitした場合は、単に次のcommitで削除するだけでは十分でないことがあります。漏えいした認証情報は無効化・再発行などの対応も検討します。

## まとめ

commitは、変更内容をGitの履歴として記録する操作です。保存とは別の操作で、PC上のcommitとGitHubへのpushも別です。変更の目的が分かる単位で、内容を説明できるコミットメッセージを付けて記録してください。
