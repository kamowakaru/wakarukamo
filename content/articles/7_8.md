## 結論

**デプロイ（deploy）とは、作ったWebサイトやアプリを公開環境へ反映して、実際のURLから使える状態にすること**です。

たとえばHTMLをPCの中で編集しただけでは、その変更を他の人は見られません。GitHub PagesやNetlify、レンタルサーバーなどへ新しい内容を反映し、公開URLで新しいページが表示されるところまでがデプロイです。

## 「作る」と「デプロイする」は別の作業

静的サイトでは、次のように考えると分かりやすいです。

1. MarkdownやHTML、CSSなどの元データを編集する
2. 必要なら公開用HTMLなどを**ビルド（生成）**する
3. 生成したファイルを公開先へ**デプロイ**する
4. 公開URLを開いて反映を確認する

ビルドは「公開できる形を作る処理」、デプロイは「その成果物を公開環境へ反映する処理」です。サイトによってはビルド不要で、HTMLファイルをそのまま公開する場合もあります。

## アップロードとの違い

FTPでレンタルサーバーへHTMLをアップロードする方法では、**ファイルをアップロードする操作がそのまま公開反映につながる**ため、アップロードとデプロイがほぼ同じ感覚になることがあります。

一方、GitHubへファイルをPushしただけでは、必ずしも公開サイトが更新されたとは限りません。GitHub Actionsなどでビルドし、その成果物をGitHub Pagesへデプロイする構成では、**Push → ビルド → デプロイ**と段階が分かれます。

## GitHub Pagesではどうデプロイする？

GitHub Pagesは、指定したブランチから公開する方法と、GitHub Actionsを使って公開する方法があります。Actionsを使う構成では、リポジトリを取得し、必要ならサイトをビルドし、公開用の成果物をアップロードしてGitHub Pagesへデプロイします。

そのため「GitHubには新しいファイルがあるのにサイトが変わらない」ときは、CommitやPushだけでなく、**Actionsのビルド・デプロイが成功しているか**まで確認します。

詳しい公開方法は[GitHub Pagesとは？](8.html)で解説しています。

## Netlifyではどうデプロイする？

NetlifyではGitリポジトリを接続すると、対象ブランチへのPushをきっかけにビルドとデプロイを実行できます。完成済みのファイルを手動で公開する方法もあります。

Netlifyでは新しいデプロイのファイルがそろってから公開版を切り替える仕組みが使われているため、更新途中のファイルが一部だけ公開される状態を避けやすくなっています。

GitHub Pagesとの違いは[Netlifyとは？GitHub Pagesとの違い・無料でWebサイトを公開する方法](7_6.html)も参考にしてください。

## ワカルカモではこうしています

ワカルカモでは、**Markdownの記事を元データとして管理し、生成スクリプトで公開用HTMLなどを作り、GitHub Actionsを通して公開へ反映する**構成を使っています。

つまり記事Markdownを書いただけでは公開完了ではありません。生成処理が正常に終わり、公開用ファイルが作られ、デプロイ後のURLで新しい記事が表示されるところまで確認します。

この構成だと、記事本文・HTML生成・公開という役割を分けて管理できます。

## デプロイに失敗したらどこを見る？

GitHub Actionsなどで自動デプロイしている場合は、まず実行履歴を開き、**ビルドで失敗したのか、デプロイで失敗したのか**を確認します。

- Markdownや設定ファイルの不備で生成スクリプトが止まった → ビルド側を修正
- 公開用成果物はできたがPagesへの反映で失敗した → デプロイ側のログや権限を確認
- デプロイ成功なのに表示が古い → 公開URL・対象ブランチ・キャッシュなどを確認

「デプロイ失敗」と一括りにせず、どの段階まで成功したかを見ると原因を絞りやすくなります。

## まとめ

デプロイは、**Webサイトの新しいバージョンを公開環境へ反映する工程**です。ローカルでファイルを作ることや、ビルドすることとは別の工程として考えると分かりやすくなります。

Webサイトを更新するときは、**編集 → ビルド → デプロイ → 公開URLで確認**までを一連の流れとして覚えておきましょう。
