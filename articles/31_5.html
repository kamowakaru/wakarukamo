GASの自動化が動かないときの原因と確認ポイント

GASの自動化が動かないときに確認したい原因を、トリガー、権限、実行履歴、シート名、利用制限、コードエラーの順に解説します。

結論

GASの自動化が動かないときは、手動実行できるか → 実行履歴に記録があるか → トリガーが正しいか → 権限や対象データに問題がないかの順に確認すると切り分けやすくなります。

「自動実行されない」と「実行されたが途中でエラーになった」は別の問題です。

1. 関数を手動実行する

最初にApps Scriptエディタから対象関数を手動実行します。

手動でも失敗するなら、トリガーより先にコードや権限、対象データを確認します。

手動では成功し、自動だけ失敗するならトリガー周辺を重点的に確認します。

2. 実行履歴を確認する

Apps Scriptの実行履歴を開き、該当時刻に処理が実行されたか確認します。

履歴がない

トリガーが作成されていない、違う関数を指定しているなどを確認します。

履歴があり失敗している

エラーメッセージと失敗した行を確認します。

この違いだけでも原因候補を大きく絞れます。

3. トリガー設定を確認する

次を確認します。

  • 実行する関数が正しい
  • イベントの種類が正しい
  • 同じトリガーが重複していない
  • 不要になった古いトリガーが残っていない

フォーム送信処理なら、フォーム側と回答先スプレッドシート側でイベントの内容が異なる点にも注意します。

4. 権限を確認する

スクリプトが新しいGoogleサービスへアクセスするようになった場合など、追加の承認が必要になることがあります。

手動実行して承認画面やエラーが出ないか確認します。

組織のGoogle Workspace環境では、管理者側のポリシーが影響する場合もあります。

5. シート名やファイルIDを確認する

const sheet = ss.getSheetByName('データ');

実際のシート名がデータ のように違っていれば取得できません。

スプレッドシートID、フォルダID、シート名など、外部データを指定する値を確認します。

6. データが空ではないか確認する

最終行を前提に範囲を作るコードでは、データが0件のときに不正な範囲になる場合があります。

if (lastRow < 2) {
  return;
}

空データを正常なケースとして扱うか決めます。

7. イベントオブジェクトを直接実行していないか

function onFormSubmit(e) {
  console.log(e.values);
}

このような関数をエディタから直接実行すると、実際のイベントが発生していないため期待するeがありません。

イベント受信部分と処理本体を分けるとテストしやすくなります。

8. 利用制限を確認する

大量メール、大量のスプレッドシート操作、長時間処理などではGASや利用サービスの制限へ達する場合があります。

具体的な上限は変更される可能性があるため、Google Apps Script公式のQuotasで現在の値を確認します。

9. ログを増やす

どこまで処理できたか分からない場合は、処理件数や主要な値をログへ出します。

ただし、パスワードやアクセストークンなど秘密情報をログへ出さないようにします。

まとめ

GASの自動化が動かない場合は、手動実行と実行履歴から「起動していない」のか「起動後に失敗した」のかを分けます。その後、トリガー、権限、対象ID・シート名、データ、利用制限を順番に確認してください。
