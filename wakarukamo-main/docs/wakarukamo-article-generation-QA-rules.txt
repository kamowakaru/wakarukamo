# ワカルカモ 記事生成・QAルール

このファイルは、ワカルカモの記事をChatGPTで生成・更新するときの基準です。
記事数を増やすこと自体ではなく、「検索した人の問題を実際に解決し、PV・信頼・自然な収益導線につなげること」を目的とします。

## 1. 基本方針

- 初心者向けに、専門用語をかみ砕いて説明する。
- 検索意図に対する答えを冒頭で明確にする。
- 一般論だけで終わらせず、具体的な操作・例・判断基準を書く。
- 文字数を増やすための説明や、AIっぽい汎用文で水増ししない。
- 短い記事でも検索意図を完全に満たせていればよい。逆に、広いテーマの親記事は薄くしない。
- 同じテーマでも検索意図が違えば別記事として入口を作ってよい。ただし内容の重複・カニバリを確認する。
- 実体験を使えるテーマでは「ワカルカモではこうしています」など、実際の運用例を積極的に入れる。

## 2. 記事構成

基本形：
- 結論
- 手順 / 原因 / 違い / 選び方など、検索意図に合った本文
- 注意点
- 必要なら「よくある質問」
- まとめ
- 関連記事・次に読む記事

H2/H3は内容に合わせて自然に使う。固定テンプレートを機械的に当てはめない。

### 親記事
- テーマ全体を理解できる十分な説明を入れる。
- 単なる子記事へのリンク集にしない。
- 各子記事へ自然に案内する。

### 子記事
- その検索意図だけで読者の疑問が解決する内容にする。
- 親記事を読まないと理解できない構成にしない。

### 孫記事
- ロングテールの具体的な疑問・トラブル・操作などに集中する。

## 3. 記事タイプ別ルール

### 操作・How-to
- 「設定してください」だけで終わらせない。
- 実際のメニュー名、ボタン、画面遷移、操作順を書く。
- 可能なら番号付きの具体的な手順にする。
- 操作後にどうなれば成功なのかを書く。
- 元に戻せるか、無料か、どこにあるかなど初心者が迷う点も補足する。

### プログラミング / API / GAS / HTML / CSS / 関数
- 必要な記事にはコピーして使えるコード・数式・設定例を入れる。
- コードを載せるだけでなく「何をしているコードか」を説明する。
- APIキー、パスワード、個人情報などの扱いに注意する。
- 実行場所や前提条件を書く。
- エラーになりやすい点があれば対処も書く。

### トラブルシューティング
基本：
症状 → 主な原因 → 確認方法 → 対処方法

- 原因を羅列するだけで終わらせない。
- 読者がどの原因に当てはまるか判断できるようにする。
- WordPress、GitHub Pages、FTP、Netlify、Wix、CDNなど環境によって対処が違う場合は分岐を書く。

### 比較・選び方
- 「目的に合わせて選びましょう」だけで終わらせない。
- 費用、難易度、自由度、管理方法、向いている人など具体的な比較軸を使う。
- 表が分かりやすい場合は比較表を使う。
- 最後に「○○ならA、○○ならB」のように判断できる形にする。

## 4. Markdown / HTML / CSS / 静的サイトの記事

役割を混同しない。
- Markdown：記事本文・コンテンツ
- HTML / テンプレート：ページ構造
- CSS：見た目
- 生成スクリプト：Markdown等から公開用HTMLを生成
- GitHub：ファイル・履歴の管理
- GitHub Actions：必要に応じて生成・公開を自動化

ワカルカモの実例を使える場合は、一般的な方法を説明した後に「ワカルカモではこうしています」として紹介する。
ワカルカモ固有の方法だけを唯一の正解として説明しない。

## 5. ChatGPT・大量記事生成の記事

- 「ChatGPTに大量に書かせれば終わり」という説明にしない。
- タイトル・記事一覧管理 → 生成 → QA → 保存 → 投稿/公開 → 公開後確認・改善、まで含めて考える。
- WordPress REST API、CSV、GitHub Pages＋Markdown、GitHub Actions、GASなど複数の実現方法がある場合は紹介する。
- 大量生成では、重複、検索意図のズレ、コード不足、誤情報、内部リンク切れ、投稿漏れなどのリスクを説明する。
- AI生成記事は公開前に内容QAを行う。

## 6. 内部リンク

- 親 → 直接の子
- 子 → 親
- 孫 → 子
を基本とする。

さらに記事全体を見て、必要なら2〜4件程度の関連リンクを追加する。
関連リンクは次の3軸で考える：
1. 階層
2. テーマ上の関連性
3. 読者が次に行う作業

無関係な記事をSEO目的だけで大量にリンクしない。
リンク先が実在するか確認する。

## 7. FAQ / Q&A

「よくある質問」は全記事へ機械的に付けない。

追加する条件：
- 本文を読んだ初心者が次に疑問に思いそうな質問が2〜4個ある。
- 本文に無理に入れるよりQ&Aにした方が読みやすい。
- 「無料？」「スマホでもできる？」「元に戻せる？」など検索意図を補完できる。

各質問には短く直接答える。
本文の単なる言い換え・水増しはしない。
FAQを入れればGoogleでリッチリザルトが出る、とは説明しない。

## 8. SEO / AIO

- タイトル、description、H2、本文の検索意図を一致させる。
- 結論や定義は簡潔に抜き出せる文章にする。
- 読者の質問に直接答えるQ→A形式が自然なら使う。
- 比較は表などで構造化する。
- タイトルは検索意図が分かるものにし、煽りすぎない。
- Search Console公開後データを使い、表示回数・順位・CTR・実際の検索語から改善する。
- 11〜20位の記事は内容や内部リンク、関連記事追加を検討する。
- 想定外の検索語で表示されている場合、見出し追加や新しい子・孫記事を検討する。
- 公開前から理論上の100点を狙って延々と長文化しない。

## 9. 正確性・鮮度

ChatGPT、OpenAI、GA4、Search Console、GitHub、WordPress、Wix、Netlify、X APIなど仕様変更が多いサービスについて、
料金、プラン制限、メニュー名、API仕様、無料枠など具体的な現在情報を書く場合は公式情報を確認する。

- 古い情報を断定しない。
- インデックス登録リクエストやサイトマップ送信で必ずGoogleに登録される、とは書かない。
- UIはバージョン等で変わる可能性がある場合、その旨を必要に応じて補足する。
- ショートカットキーなど細かい操作も推測で書かない。

## 10. アフィリエイト

- article-management.csv の「アフィ候補」を参考にする。
- 現時点の記事生成では、指定がない限りアフィリエイトURLそのものは挿入しない。
- 読者に本当に役立つ場合のみサービス・商品を自然に紹介する。
- 売るために結論を歪めない。
- 無料の選択肢や、向いていないケースも必要なら説明する。
- 将来CTAを追加しても不自然にならない文章構造にする。

## 11. 公開前QA

### 構造
- article_no / No. は正しいか
- タイトルとCSVが一致しているか
- category / tags / description / frontmatter は正しいか
- IDの重複・欠番・誤りがないか
- ファイル名・リンク先が正しいか

### 内容
- タイトルの質問に本文が直接答えているか
- 冒頭の結論だけで大筋が分かるか
- 一般論だけになっていないか
- 操作記事に具体的な操作があるか
- コードが必要な記事にコード例があるか
- トラブル記事に確認方法と対処方法があるか
- 比較記事に具体的な比較軸があるか
- 親記事が薄いリンク集になっていないか
- 初心者が途中で「で、どうすれば？」となる箇所がないか

### 品質
- 同じ汎用段落を多数の記事へコピペしていないか
- FAQが機械的・重複的になっていないか
- AIっぽい抽象文や水増しがないか
- 他記事と検索意図が重複しすぎていないか
- 内容に矛盾がないか
- 古い仕様・料金・UIを断定していないか
- ワカルカモの実体験を入れる価値がある記事では入っているか

### リンク
- 親子リンクが適切か
- 関連・次の行動への内部リンクがあるか
- リンク切れがないか
- 「次に読む記事」が本文と本当に関連しているか

### 収益
- アフィ候補の紹介が不自然でないか
- 商品・サービスを売るためだけの記事になっていないか
- 読者にとってより適切な無料・別手段がある場合、それを隠していないか

## 12. 大量生成時の追加QA

大量の記事を生成した場合、機械チェックだけで「公開品質」と判定しない。

機械チェック向き：
- 記事数
- ID重複
- frontmatter
- CSVとの照合
- 内部リンク切れ
- コードブロック有無
- 文字数の極端な異常
- FAQ構造
- 同一段落の大量重複

内容確認が必要：
- 検索意図への回答
- 手順の具体性
- 情報の正確性
- コードの妥当性
- 比較の有用性
- AIっぽい文章
- 実際に初心者が解決できるか

「一定文字数以上だから合格」「見出し数が足りているから合格」のような機械判定だけで公開可としない。

## 13. ワカルカモで実際に起きたQA上の教訓

- 大量生成した記事が一定文字数あっても、本文が汎用テンプレート中心なら品質は低い。
- GAS/API/HTML/CSS等の記事では、説明だけでコード例がないと実用性が落ちる。
- FAQをほぼ全記事へルールベースで付けると、似た質問が大量に発生しやすい。
- 同じ注意書きを多数の記事へ繰り返すとAI生成感が強くなる。
- 自動QAは異常検出には強いが、検索意図を本当に満たしているかまでは保証できない。
- 大量公開後もSearch Consoleと実際の閲覧で改善する。

## 14. 記事生成時の最終指示

記事を生成する前に article-management.csv 全体を確認し、
- 既存記事との重複
- 適切な階層
- 関連記事
- 次の行動につながる記事
を確認する。

記事生成後はこのQAルールを使って自己チェックし、問題があれば修正してから成果物に含める。

目的は「記事を作ったこと」ではなく、
検索した人が「わかった」「できた」と感じられる記事を公開すること。
