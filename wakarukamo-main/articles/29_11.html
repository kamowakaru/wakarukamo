GitHubで間違って上書きしたファイルを元に戻す方法｜Revertの仕組みと手順を解説

GitHubで間違って上書きしたファイルを元に戻す考え方を、履歴確認、Revert、新しいCommitでの復元に分けて解説します。

結論

GitHubでファイルを間違って上書きした場合は、どのCommitで変更したかを確認し、過去の内容を取り出して新しいCommitとして戻すか、対象CommitをRevertして変更を打ち消す方法を検討します。

「元に戻す」といっても、履歴そのものを消す方法と、逆の変更を新しく記録する方法は別です。初心者は共有済みの履歴を安易に書き換えず、変更履歴を残したまま復元する方が状況を追いやすくなります。

最初に履歴を確認する

対象ファイルやリポジトリのCommit履歴を開きます。

どのCommitまでは正しく、どのCommitから意図しない内容になったか確認します。

複数ファイルを同時に変更したCommitなら、ファイル1つだけ戻したいのか、Commit全体を打ち消したいのかも分けます。

1ファイルだけ戻す場合

過去の正しい版を確認し、その内容を現在のファイルへ戻して、新しいCommitとして記録する方法があります。

この方法なら「誤って上書きしたCommit」と「復元したCommit」の両方が履歴に残ります。

Revertとは

GitのRevertは、特定のCommitが行った変更を打ち消すための新しいCommitを作る考え方です。

過去のCommit自体を履歴から消すのではありません。

共有済みの変更を元に戻す場面では、履歴を保ったまま変更を打ち消せる利点があります。

Revert前に変更範囲を見る

対象Commitに、戻したいファイル以外の変更も含まれている場合があります。

Commit全体をRevertすると、それらも打ち消される可能性があります。

差分を確認せず「この日時だから」と選ばないようにします。

GitHubの画面でRevertできる場面

GitHubでは、Pull Requestなど特定の画面・条件でRevert操作を利用できる場合があります。

すべてのファイル変更で同じ場所にRevertボタンが出るとは限りません。

画面上で利用できない場合は、GitコマンドやGitHub Desktopと組み合わせて復元します。

GitHub Desktopで確認する

GitHub DesktopではCommit履歴や変更内容を確認できます。

復元操作を行う前に、現在のローカル変更が残っていないか確認します。未Commitの作業がある状態で復元を進めると、別の変更と混ざることがあります。

resetとの違いに注意する

Gitには過去の状態へ履歴を動かすresetもありますが、Revertとは動作が異なります。

すでにGitHubへPushして他の人と共有している履歴を安易に書き換えると、共同作業へ影響することがあります。

意味が分からない状態で強制Pushまで行わないようにしてください。

復元後に確認する

元に戻した後は、対象ファイルだけでなく関連するページや機能も確認します。

Webサイトなら表示、リンク、CSS、JavaScriptなど、上書きによる影響が残っていないか確認します。

秘密情報の上書きは別対応

APIキーなどを誤ってGitHubへPushした場合、ファイルを過去の状態へ戻しても漏えい対策として十分とは限りません。

認証情報を無効化・再発行し、必要なら履歴からの削除についてGitHub公式の手順を確認します。

まとめ

間違った上書きを戻すときは、まずCommit履歴と差分を確認します。1ファイルなら正しい内容を新しいCommitで復元し、Commit全体を打ち消すならRevertを検討します。共有済みの履歴は、意味を理解せず書き換えないようにしてください。
